# Подписанные обновления Bot4VPS

Web, консольное меню и `install.sh update` используют один установщик обновлений.
Проверка ищет стабильный GitHub Release новее установленной версии.
Новая ветка `main` сама по себе больше не является доступным обновлением.

Первичная установка также выбирает последний стабильный GitHub Release,
проверяет Ed25519-подпись, размер/SHA256 архива, точную ревизию и версию.
Загрузка и проверка проходят во временном каталоге до замены существующей
установки. При отсутствии подписанного релиза установка останавливается;
перехода на main нет. Git-клон для установки больше не нужен.

Самостоятельный `install.sh` берётся из вложений стабильного релиза:

```bash
curl -fsSL https://github.com/crashdmd/Bot4VPS/releases/latest/download/install.sh | sudo bash -s -- install
```

В нём встроены проверяющий код и открытый ключ, полученные вместе с
доверенным установщиком. Для первой проверки используется системный пакет
`python3-cryptography`; зависимости самого Bot4VPS устанавливаются только
после проверки архива, с `--require-hashes` из его lock-файла.

Android APK распространяется через [`crashdmd/Bot4VPS-Mobile`](https://github.com/crashdmd/Bot4VPS-Mobile), каталог `apk/` в ветке `main`.
Опубликуйте `Bot4VPS-Mobile-<версия>-release.apk` и `apk/release.json` вместе.
Метаданные фиксируют `version`, возрастающий `versionCode`, имя, размер и SHA-256 APK.
Источник для приложения и сервиса:

```text
https://api.github.com/repos/crashdmd/Bot4VPS-Mobile/contents/apk/release.json?ref=main
```

Файлы читаются через GitHub Contents API с `Accept: application/vnd.github.raw+json`:
он возвращает исходные байты из `apk/`, без обращения к отдельному raw-хосту.

Android проверяет размер, SHA-256, пакет, версию и совпадение подписи с установленным
приложением. Новая сборка с тем же именем версии устанавливается при большем
`versionCode`. Отдельный GitHub Release для APK не требуется; его можно создать
дополнительно, но обновление читает каталог `apk/` ветки `main`.

Сервис проверяет этот источник отдельно от подписанных серверных релизов:
суточная автоматическая проверка и общая кнопка «Проверить» проверяют оба продукта
с независимыми результатами. В «Настройки → Мобильное приложение» также есть
«Проверить обновление APK». Перед скачиванием/выдачей через Telegram выполняется проверка,
если последняя была более часа назад.

Сервис хранит единственный APK и метаданные в рабочих данных:

```text
data/mobile-release/
├── Bot4VPS-Mobile.apk
└── release.json
```

Сначала новая версия скачивается во временный файл рядом. Размер и SHA-256
проверяются до атомарной замены текущего APK и публикации локальных метаданных.
При ошибке загрузки или проверки текущий файл остаётся на месте. Старый APK
после успешной замены не хранится; история выпусков остаётся в GitHub.
Начатые Web/TG-передачи завершаются через уже открытый файловый дескриптор.
Короткая блокировка публикации согласует APK с метаданными; незавершённая
замена восстанавливается перед выдачей. Рабочие lock/state-файлы и временные
файлы не доступны через скачивание APK.

Служба `bot4vps` записывает только рабочие данные; root-помощник для APK не нужен.
Исходная копия из прежнего `ui/mobile/` переносится с проверкой в `data/`, после
чего `ui/mobile/` удаляется из сервиса. При первой установке без APK он получается
из GitHub. Серверные релизы и их подпись продолжают использовать Bot4VPS.

В релизе должны быть три дополнительных файла:

- `Bot4VPS-update.json` — описание версии, тега, точного Git-коммита,
  имени/размера/SHA256 архива и изменений; подписано Ed25519.
- `Bot4VPS-X.Y.Z.tar.gz` — именно тот архив, который описан и подписан.
- `install.sh` — самостоятельный установщик из того же проверенного коммита.

Открытый ключ доверия поставляется с установленным Bot4VPS. Ключ из
загруженного описания или архива не принимается. Закрытый ключ нужен
только при выпуске релиза; устанавливать его на пользовательские VPS не нужно.

При установке проверяются:

1. Подпись описания и соответствие выбранной версии/тегу/репозиторию.
2. Размер и SHA256 при загрузке архива; недопустимые перенаправления блокируются.
3. Git-коммит в метаданных архива и версия исходников.
4. Запуск установленной версии после резервной копии и замены кода.

После разделения прав проверку и замену кода выполняет отдельный root-помощник
из `/usr/lib/bot4vps-helper`. Он самостоятельно проверяет подпись и параметры,
использует защищённые staging/backup в `/var/lib/bot4vps-helper`, а runtime
state записывает с UID приложения. Релизы без поддержки разделения прав
отвергаются до замены кода.

Проверка подписи повторяется отдельным процессом перед загрузкой и
распаковкой. Проверяющий код копируется из текущей установки до получения
новых файлов. Несовпадение подписи, версии, ревизии, размера или хеша
останавливает установку до изменения кода. При неудачном запуске новой
версии сохраняется автоматический откат к предыдущему коду.

Для Web проверяется HTTP health endpoint с ожидаемой версией. Для режима
Telegram-only проверяется стабильный запуск systemd-службы, поскольку HTTP
listener в этом режиме отсутствует. Настройки, серверы и рабочие данные
сохраняются; локальные изменения исходников следует сохранить отдельно.

## Выпуск релиза

Первый постоянный ключ уже подготовлен для этого перехода. Его нужно
сохранить отдельно и сделать закрытую резервную копию. Не генерируйте
замену при подготовке каждой среды, установке или сборке. Ключ обновлений
сервера отдельный от ключа подписи Android APK.

`tools/sign_update.py` создаёт архив **указанного коммита**. Несохранённые
изменения рабочего дерева в него не попадают. Сначала проверьте и сохраните
готовые изменения в Git; в коммите должны быть правильная `APP_VERSION` и
секция этой версии в `core/update/changelog.md`.

Пример на машине издателя:

```bash
python3 tools/sign_update.py \
  --source /path/to/Bot4VPS \
  --commit <полный-SHA-коммита> \
  --key /secure/bot4vps-update-release.key \
  --output /path/to/release-files
```

Перед коммитом изменений проверяющего кода выполните
`python3 tools/build_installer.py`: он обновляет встроенный bootstrap в
`install.sh`. Команда подписи откажет, если встроенный код не совпадает с
исходниками выбранного коммита.

Файл ключа должен иметь права `0600`; храните его вне публикуемых исходников.
Команда сверяет ключ с открытым ключом доверия, отказывает при рабочих
данных/ключах в Git-снимке и не перезаписывает существующие файлы релиза.
Она не выполняет commit, push или публикацию. После проверки опубликуйте
полученные три файла в GitHub Release с указанным тегом. Не подменяйте
подписанный архив стандартным автоматически созданным ZIP/TAR GitHub:
это другой набор байтов и другая контрольная сумма.

Явное создание нового ключа предусмотрено только для первоначального
настройщика отдельного проекта:

```bash
python3 tools/sign_update.py --create-key /secure/bot4vps-update-release.key
```

Эта команда не заменяет существующий ключ и не меняет открытый ключ
доверия в приложении. Ротация ключа опубликованного продукта требует
отдельного плана перехода.

## Старые установки и откат

При переходе root-установки 6.5 на 7.0 миграция выполняется автоматически
отдельным установщиком. Новый runner запускает его до restart; для уже
выпущенного updater предусмотрена передача из самого раннего bootstrap,
до инициализации UI. Учитываются journal, systemd User и MainPID, а не только
euid. Успешная новая установка и обновление используют одну модель служб.
Hash lock Certbot также поставляется внутри `core/migration/privileged/`:
старый updater 6.5.0 переносит `core/`, но не знает новых файлов зависимостей
в корне. Помощник использует эту защищённую копию при установке Certbot;
подготовка релиза проверяет её совпадение с корневым lock-файлом.
Состояния, снимок JSON/ключей/SQLite, отказ helper, восстановление прав и
поздний откат старого updater описаны в [root-separation.md](root-separation.md).
Ручной перенос кода и диагностика ошибок описаны в [инструкции миграции](root-separation.md#ручной-переход-с-65-на-70).

Версии без проверки подписи сначала нужно перевести на код с этой
проверкой через доверенную поставку. Новая проверка не может защитить
операции, которые выполняет старый установщик.

Проверка подписи определяется целевой версией. Для 7.0.0 и новее она
обязательна при обновлении и откате. При откате на версию ниже 7.0.0
подпись не проверяется: старые релизы опубликованы до этой схемы. Исполнитель
сам выбирает стабильный релиз из фиксированного GitHub-репозитория Bot4VPS,
разрешает его тег в Git-коммит и получает архив этого коммита по HTTPS.
URL, флаг исключения или коммит от интерфейса не служат источником доверия.
Исключение не применяется к неподписанной 7.0 или более новой версии.

Откат с 7.0 на старую версию включает обратную миграцию. До запуска старой
версии возвращаются root-служба, CLI, JSON-файлы в корне установки и
история конфигурации в backup/. Код, все локальные рабочие данные, ключи,
права, текущий unit и launcher 7.0 сохраняются в защищённой копии. Лишь
после успешной проверки старой службы переход завершается и помощник
выключается. Любая ошибка до завершения, включая прерывание процесса,
возвращает 7.0 с данными и правами; служба снова проходит проверку запуска.
При следующем обновлении на 7.0 миграция выполняется заново с текущими данными.
Старый релиз использует собственные зависимости и возможности интерфейсов;
мобильное приложение нового выпуска может потребовать совместимую версию.

Автоматическое восстановление локальной защитной копии после неудачной
установки продолжает работать и не требует скачивания.

Проверка подписи обновлений не зависит от включения пароля панели или 2FA.
Эти настройки входа пользователь выбирает самостоятельно. Первичная
установка остаётся отдельной точкой доверия: установщик и исходный открытый
ключ должны быть получены из доверенного источника.
