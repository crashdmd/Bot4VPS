# Фиксация Python-зависимостей

`requirements.in` содержит прямые зависимости проекта. `requirements.txt` —
генерируемый lock всей транзитивной цепочки: точные версии `==`, SHA-256
дистрибутивов и маркеры Python/платформы. Его устанавливают существующие
install, update и self-restore; отдельный менеджер пакетов на VPS не нужен.

В публичном репозитории и исходном архиве релиза сохраняются все четыре файла:

| Файл | Назначение |
|---|---|
| `requirements.in` | Прямые зависимости сервиса для пересборки lock |
| `requirements.txt` | Готовый runtime lock для установки: точные версии и хеши |
| `requirements-certbot.in` | Прямые зависимости опционального Certbot |
| `requirements-certbot.txt` | Готовый согласованный lock для установки Certbot |

Эти файлы не содержат секретов. `.in` нужны разработчику, а установка использует
готовые `.txt`; наличие файлов Certbot в поставке не включает его автоматически.
В исходниках помощника также поставляется `core/migration/privileged/requirements-certbot.txt`:
это синхронизируемая копия для независимого root-помощника, которую обновляет
`tools/lock_dependencies.py` вместе с основным Certbot lock.

```bash
python3 -m venv venv
venv/bin/python -m pip install --require-hashes -r requirements.txt
venv/bin/python -m pip check
```

Lock рассчитан для Python 3.10 и новее. Например, `websockets` имеет разные
зафиксированные версии для Python 3.10 и 3.11+, а `exceptiongroup` нужен только
на 3.10. Начальные версии взяты из проверенной среды проекта; точные версии
для других сред выбирает resolver по метаданным совместимости. Универсальное
разрешение не заменяет исполнение тестов на каждом Python и архитектуре.

Опциональный Let's Encrypt использует `requirements-certbot.txt`, скомпилированный
совместно с runtime и ограниченный его lock: установка Certbot в venv не должна
незаметно обновлять пакеты сервиса. Системный Certbot, если уже установлен,
остаётся инструментом ОС. Его версии управляет пакетный менеджер ОС.

Тестовый репозиторий остаётся отдельным. `tests/ci/requirements.in` содержит его
прямые зависимости, а `tests/ci/requirements.txt` — полный hash lock, согласованный
с runtime. CI устанавливает оба lock-файла; dev-пакеты в релиз сервиса не входят.

## Ошибки загрузки зависимостей

`SSLEOFError` / `UNEXPECTED_EOF_WHILE_READING` при загрузке с
`files.pythonhosted.org` означает обрыв TLS-соединения. Проверьте доступ к
PyPI с сервера, DNS и сетевой прокси; повторите установку после восстановления
связи. Если основной источник недоступен, можно использовать доверенное
HTTPS-зеркало, сохранив проверку SHA-256 из `requirements.txt`, например:

```bash
cd /opt/bot4vps
venv/bin/python -m pip --isolated install \
  --index-url https://mirrors.aliyun.com/pypi/simple/ \
  --require-hashes -r requirements.txt &&
venv/bin/python -m pip check
```

Несовпадение хеша означает отказ установки: не удаляйте хеши из lock-файла
и не отключайте проверку TLS. Отсутствие нужной версии на зеркале требует
другого доступного источника, а не произвольного обновления пакетов.
Понижение отдельных пакетов до версий из lock-файла ожидаемо, если в прежнем
`venv` уже были более новые версии. Успешное завершение pip и
`No broken requirements found` подтверждают установку согласованного набора;
миграцию и запуск Bot4VPS проверяют отдельно.

## Обновление lock-файлов

Для разработчика нужен `uv 0.9.21` в отдельной среде; production venv не меняйте.

```bash
python3 -m venv /tmp/bot4vps-lock-tools
/tmp/bot4vps-lock-tools/bin/python -m pip install uv==0.9.21
python3 tools/lock_dependencies.py --uv /tmp/bot4vps-lock-tools/bin/uv
```

Помощник проверяет версию uv и пересобирает runtime, Certbot и тестовый lock
(последний — при наличии тестового checkout). Существующие pins сохраняются;
для осознанного обновления пакета используйте `--upgrade-package ИМЯ`.
При изменении общих зависимостей сначала пересобирается runtime, затем остальные
lock-файлы с его ограничениями. Хеши получает resolver; не редактируйте их вручную.

Проверяйте установку в новом venv, `pip check` и тесты в изолированной копии
исходников без боевых config, ключей, БД и журналов. Изменения code/test lock
коммитьте в соответствующие репозитории. Updater сравнивает SHA-256
`requirements.txt` и запускает pip при его изменении. Для восстановления старых
архивов поддерживается их прежний requirements: hash lock применяется новым кодом.
