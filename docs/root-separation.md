# Разделение локальных привилегий

С Bot4VPS 7.0 основной сервис работает от системного пользователя `bot4vps`,
а локальные операции с правами root выполняет отдельный помощник.
`install.sh` и штатное обновление включают разделение автоматически.
При ручном переносе исходников или незавершённом переходе используйте инструкцию ниже.

## Ручной переход с 6.5 на 7.0

Инструкция предназначена для установленного Bot4VPS в `/opt/bot4vps` на системе
с systemd. Все команды выполняются **от root, без sudo**. `id -u` должен
показывать `0`. На диске уже должен быть доверенный код 7.0 с установщиком
`core/migration/privileged/install.py`; исходники сами по себе не меняют
пользователя работающей службы и установленную копию помощника.

1. Сохраните прежний код и отдельную копию настроек, списка серверов, ключей
   (включая мастер-ключ), `data/`, `logs/`, `scripts/` и `backup/`. При уже
   выполненном разделении копируйте реальные файлы из `data/runtime/`,
   а не только ссылки в корне. Внешний каталог архивов, по умолчанию
   `/var/backups/bot4vps`, также должен сохраняться. До завершения перехода
   держите доступ к серверу через SSH или консоль провайдера.
2. Остановите службу **до замены кода и установки зависимостей**:

   ```bash
   systemctl stop bot4vps.service
   ```

   Перенесите новый код, сохранив рабочие данные и `venv`. Для полной копии
   остановленных данных используйте этот момент; затем продолжайте переход.
3. Установите зависимости из нового lock-файла и запустите миграцию:

   ```bash
   cd /opt/bot4vps
   venv/bin/python -m pip --isolated install --require-hashes -r requirements.txt &&
   venv/bin/python -m pip check &&
   python3 -I core/migration/privileged/install.py
   ```

   `&&` останавливает последовательность при ошибке. Не запускайте миграцию
   после неудачной установки пакетов. Установщик использует системный Python,
   создаёт защитный снимок данных, переносит JSON, устанавливает помощник,
   переключает unit и проверяет запуск службы. Старые ссылки на JSON остаются
   в корне установки. Код и `venv` сохраняют root-владение.
4. Проверьте результат:

   ```bash
   systemctl show bot4vps.service -p User -p Group -p MainPID
   systemctl is-active bot4vps.service bot4vps-helper.service
   readlink /opt/bot4vps/config.json
   ```

   Ожидаются `User=bot4vps`, `Group=bot4vps`, ненулевой `MainPID`, два состояния
   `active` и ссылка `data/runtime/config.json`. Затем откройте Web или проверьте
   Telegram в режиме без Web; убедитесь, что список серверов и настройки сохранены.
   Если Mobile API включён, проверьте подключение ранее привязанного телефона.

Повторный запуск этой же команды на уже разделённой установке обновляет
помощник и проверяет текущую конфигурацию без повторного переноса JSON.
`--no-start` предназначен для подготовки с отложенным запуском: такой запуск
не подтверждает работоспособность основного сервиса.

## Если переход остановился с ошибкой

Сначала сохраните полный текст ошибки и проверьте состояние, прежде чем
повторять операцию:

```bash
systemctl status bot4vps.service bot4vps-helper.service --no-pager
journalctl -u bot4vps.service -u bot4vps-helper.service -n 100 --no-pager
```

Журнал миграции находится в `/var/lib/bot4vps-helper/migration.json`.
Его состояние можно прочитать без вывода содержимого защитных снимков:

```bash
python3 -c 'import json; from pathlib import Path; print(json.loads(Path("/var/lib/bot4vps-helper/migration.json").read_text())["status"])'
```

После обычной миграции с проверкой запуска ожидается `complete`. Если ошибка
возникла ещё на предварительной проверке, нового журнала может не быть.

| Ошибка / ситуация | Действия |
|---|---|
| `В backup storage есть посторонние файлы` | Проверьте путь `backup.storage.root` в конфигурации и содержимое этого каталога. Допускаются `bot4vps/`, `servers/`, `imports/`, `staging/`, `quarantine/`, `tmp/`. Посторонние файлы сохраните и перенесите за пределы выделенного storage, затем повторите миграцию. |
| В storage только перечисленные каталоги, но проверка всё равно отклоняет `tmp/` | Проверьте, что перенесён актуальный `core/migration/privileged/install.py`: он допускает существующий `tmp/` и сохраняет его содержимое. Удалять временный каталог ради перехода не требуется. |
| `tmp в backup storage должен быть обычным каталогом`, ссылка, hardlink или специальный файл | Проверьте указанный путь и сохраните его содержимое. Замените неподходящий объект обычным выделенным каталогом/файлом; не обходите проверку владельцев и ссылок. |
| `Backup storage должен находиться вне установки` | Выберите отдельный каталог за пределами `/opt/bot4vps`, перенесите архивы и согласуйте `backup.storage.root` до повторной миграции. |
| `Venv должен принадлежать root без записи другим пользователям` | Проверьте владельцев и права именно `venv`. Не выполняйте `chown -R bot4vps /opt/bot4vps`: приложению разрешена запись только в рабочие данные. |
| `Drop-in меняет границу привилегий` | Проверьте `/etc/systemd/system/bot4vps.service.d/*.conf`. Уберите конфликтующие переопределения `User`, `Group`, команд запуска и ограничений записи, сохранив нужные настройки. Установщик создаёт фиксированный unit. |
| Ошибка pip / TLS при скачивании пакетов | Завершите установку зависимостей и `pip check` до миграции. [Диагностика загрузки зависимостей](dependencies.md#ошибки-загрузки-зависимостей). |
| Помощник или основной сервис не запустился | Прочитайте журналы обоих unit. Исправьте конкретную причину и повторите ручной запуск установщика. Автоматическая миграция после отказа не повторяется, чтобы не зациклить перезапуски. |

При ошибке первого переключения установщик возвращает прежние пути, владельцев
и unit из своего журнала. Он **не возвращает код 6.5**, который вы заменили
вручную. Если службу остановили перед переходом, она также может оставаться
остановленной после отката. Для возврата к 6.5 нужен сохранённый совместимый
код и его зависимости; запускать 7.0 от root вместо завершения миграции нельзя.

Аварийный возврат прав и путей владельцем выполняется командой
`python3 -I /opt/bot4vps/core/migration/privileged/install.py --rollback`
при наличии журнала. Она сохраняет текущие данные и не заменяет штатный откат
версии; применяйте её после проверки состояния и подготовки прежнего кода.
Журнал содержит защитные данные установки, поэтому не публикуйте его целиком.

## Границы прав и хранения

Основной процесс работает от `bot4vps`. Root-помощник устанавливается
отдельно в `/usr/lib/bot4vps-helper`, запускается системным Python с `-I`
и не импортирует приложение. Основной unit даёт 45 секунд на остановку;
каталог `/run/lock/bot4vps` создаётся помощником до его запуска, в том числе
после reboot. Протокол — ограниченный JSON по локальному
Unix-сокету, с проверкой реального UID обеими сторонами, закрытыми схемами
и независимой проверкой аргументов. Изменение unit реконструирует фиксированную
команду и всегда сохраняет `User=bot4vps`; директивы чужого unit не применяются.

JSON-файлы живут в `data/runtime/`. Прежние пути в корне установки — ссылки
для чтения и совместимости; атомарные писатели и блокировки работают по
реальным путям. CLI запускает операции с данными от `bot4vps`, включая запуск
владельцем через sudo. Удалённые SSH/SFTP и sudo сохраняют прежние учётные записи.
История конфигурации и servers.json перенесена в `data/config-backup/`.
Прежний `backup/` защищён root: старый updater сохраняет доступ к своему
пути `backup/update_backup_*` для аварийного возврата и очистки.

Журналы владения firewall, staging обновлений, снимки кода и журнал миграции
находятся в `/var/lib/bot4vps-helper` и недоступны приложению для записи.
Self-restore распаковывает данные без root, не применяет численные UID из
архива, реконструирует unit и восстанавливает код только из защищённого
снимка с совпадающими SHA-256. Для архивов с другим кодом доступен выбор рабочих
данных при подтверждённой версии Bot4VPS 7.0+; замена кода выполняется подписанным
обновлением. Self-restore архива ниже 7.0 или с неизвестной фактической версией
запрещён полностью, включая выбор только данных. Версия читается из
`core/version.py` всего архива перед prepare и повторно apply, до защитной
копии и остановки службы. Для старого архива сначала нужен штатный откат до
совместимой версии, затем восстановление. Новые собственные копии используют
контейнер B4VS с TAR/manifest v3, который старые восстановители отвергают до
распаковки; опциональное шифрование B4VE сохраняется. Формат серверных копий
не меняется. Подробнее: [backup-core.md](backup-core.md).
Откат на релиз ниже 7.0 выполняет обратную миграцию в прежнюю root-архитектуру.
Для 7.0 и новее поддержка разделения прав и подпись обязательны.

Обратная миграция имеет отдельный защищённый журнал `regression.json` и
снимок всех локальных рабочих данных, ключей, истории, прав, unit и CLI.
Сначала останавливается служба, создаётся снимок и проверяется архив старого
GitHub-релиза. Затем возвращаются прежние пути JSON и истории конфигурации,
root-владение и фиксированный unit. Старая версия запускается для проверки;
только успешный запуск завершает переход и выключает помощник. При сбое
или смерти исполнителя возвращаются прежний код 7.0, байты данных и права,
текущие порт/TLS, launcher и работающий помощник, затем проверяется 7.0.
Внешние архивы backup не перемещаются; сохраняются права их каталогов.

После следующей успешной миграции с проверкой здоровья выполняется ротация
защитных архивов отката: сохраняются три последних снимка в каждой семье
(`regression-snapshots`, `regression-runtime-*`, архивные журналы
`migration-before-regression-*.json`). Копии, на которые ссылается текущий
журнал, сохраняются. Незавершённый откат или восстановление запрещают ротацию.
Очистка никогда не выполняется до успешной проверки запуска новой службы.

Certbot использует отдельное хранилище помощника. Временное разрешение TCP/80
и остановка собственной панели на этом порту имеют журнал намерений и
восстанавливаются при перезапуске помощника. Запросы обрабатываются
ограниченным числом отдельных процессов; UID не хранится в общем изменяемом
состоянии. Мутации сериализуются root-owned flock; Mobile API firewall и
чтения имеют отдельные блокировки, чтобы startup/shutdown службы не
взаимоблокировались с обновлением. Systemd-действие сначала ставится в
очередь, ожидание результата проходит вне IPC-блокировки. Посторонние службы не останавливаются.

## Инвентаризация

| Операция | Текущий владелец | Требуемая граница |
|---|---|---|
| Web/API/TG, мониторинг, очереди, SSH/SFTP | основной процесс | пользователь bot4vps; удалённый sudo сохраняется |
| Перезапуск из API и CLI | routers/system.py, cli/systemd_ops.py | только собственный unit через помощника |
| Обновление и откат | update/updater.py и runner.py | независимая подпись, защищённый staging, код и venv root |
| Смена порта и режима Web/TG | web_port.py, cli/systemd_ops.py, install.sh | фиксированная схема unit, без передачи произвольного ExecStart |
| HTTPS, сертификаты и продление | web_tls.py, install.sh | данные сертификата bot4vps; certbot и /etc/letsencrypt через помощника |
| Локальный API firewall | device_access/firewall.py | помощник; журнал владения правилами защищён от приложения |
| Web firewall и временный HTTP challenge | cli/systemd_ops.py, install.sh | только фиксированные TCP-порты; сохранять чужие правила |
| Код первого администратора | setup_code.py, install.sh | root-owned drop-in, доступ bot4vps через помощника, TTL сохраняется |
| Часовой пояс и журнал службы | timezone.py, system router, CLI | фиксированные операции, только собственный journal |
| Системная CLI-команда | cli/bootstrap.py | root-owned launcher; CLI с данными работает от bot4vps |
| Self-backup | backup/manager.py, bot4vps_sources.py | чтение кода и unit; storage/locks доступны bot4vps |
| Self-restore | backup/self_restore.py и runner | непривилегированная распаковка данных; unit реконструируется; код только доверенный |
| Restore удалённого сервера, full-root backup | backup/restore_apply.py | прежние SSH-права, без локального root |
| Config/server backup и аварийный restore | config.py, storage.py, CLI | одна схема путей/прав, согласованные flock и atomic replace |
| Установка, переустановка, удаление | install.sh | root; не удалять внешние архивы и защитные копии при keep-data |

Код/venv/помощник/юниты и защитные копии не доступны приложению для записи.
Весь `/opt/bot4vps` рекурсивно пользователю не передаётся. Сохраняются пути
SSH-ключей. Перед переключением сохраняются unit, drop-ins и численные
UID/GID/mode изменяемых файлов. Миграция должна откатываться при ошибке health.

## Проверки перед переключением

- Unix peer UID, закрытая схема запросов, неизвестные операции, инъекции
  systemd/аргументов, symlinks/hardlinks, конкурентные запросы и перезапуск помощника.
- Установка и миграция; чтение/запись/rotation/quarantine JSON; SQLite/WAL;
  config restore; мастер-ключ и SSH-ключи; пользовательские scripts.
- Web, отдельный Mobile API, TG-only, SSH/SFTP, очереди и фоновые задачи.
- API/CLI restart; Web/TG переключение; порт/TLS rollback; LE renewal.
- UFW/firewalld/nftables: свой журнал, сохранение чужих правил, восстановление
  прежнего порта, незавершённая очистка после рестарта.
- Подписанное обновление, плохая подпись/hash, pip/health failure, защищённый
  откат; helper не исполняет скрипт или job, предоставленный приложением, от root.
- Все self-backup/self-restore варианты, старые архивы, шифрование, выбор
  отдельных путей, отмена до mutation fence, восстановление после аварии.
- Тесты запускаются только в изолированной source-копии без production runtime.

## Автоматический переход на 7.0

Канонический установщик — `core/migration/privileged/install.py`. Исходники
помощника доставляются внутри `core/`: этот каталог уже входит в allowlist
старого updater. После установки помощник работает с отдельной защищённой
копией в `/usr/lib/bot4vps-helper`, без импортов из приложения.

Новый updater запускает отдельный root-установщик перед restart старой службы.
Уже выпущенный updater такого hook не знает: при запуске 7.0 старая root-служба
проверяет systemd User/MainPID и передаёт миграцию фиксированному detached unit
`bot4vps-privilege-migration`, затем завершается до загрузки конфигурации/UI.
Непривилегированная служба установщик не запускает. Проверка только euid
недостаточна: учитывается защищённый журнал.

| Состояние | Журнал | Поведение |
|---|---|---|
| legacy_root | отсутствует | подготовить пользователя и новое разделение |
| migration_in_progress | preparing / switched | сначала вернуть незавершённую транзакцию |
| privilege_separated | complete | проверить/обновить существующую конфигурацию без повторного переноса |
| migration_failed | rolled_back / неизвестное состояние | не запускать 7.0 от root; updater возвращает предыдущий код |

После остановки старой службы сохраняются JSON, ключи, история конфигурации и
SQLite через SQLite backup API. Снимок имеет SHA-256, fsync и исходные UID/GID/mode;
WAL/SHM не копируются как независимые файлы. При отказе helper или health
возвращаются данные, пути, unit и права. Намерения записываются до rename.
Установщики сериализованы отдельным root-owned flock; автоматический повтор
после отказа запрещён, чтобы исключить цикл миграций.

Если старый updater уже после успешной миграции возвращает код 6.5, помощник
обнаруживает отсутствие поддержки разделения в защищённом дереве. Отдельный
фиксированный root recovery unit возвращает прежнюю службу и снимок данных.
При обычной замене кода helper удерживает control.lock, поэтому временное
отсутствие файлов не запускает legacy recovery. Это аварийный возврат
неудачного обновления; успешная 7.0 продолжает работать только от bot4vps.

## Устройство миграции

Ручная процедура приведена [в начале документа](#ручной-переход-с-65-на-70).
`core/migration/privileged/install.py` сохраняет unit, права и
владельцев, останавливает службу, подготавливает пользователя/данные/помощника,
запускает новую службу и проверяет health. При неудаче прежние пути, владельцы
и unit восстанавливаются автоматически. Журнал находится в
`/var/lib/bot4vps-helper/migration.json`; аварийный возврат выполняется тем же
установщиком с `--rollback`. `install.sh` применяет эту процедуру автоматически.
Все вызовы установщика и импорты помощника используют
`core/migration/privileged/`. Этот путь доставляется как при полной установке,
так и при обновлении старым updater 6.5.0.
Ручной `--rollback` сохраняет текущие данные; прежний совместимый код нужно
вернуть отдельно. Он не разрешает запуск root-интерфейсов самой 7.0.
Старые code-backup каталоги сохраняются отдельно от пользовательских архивов.
Не изменяются владельцы посторонних файлов в указанном backup storage.
Существующий каталог `tmp/` внутри backup storage допускается при миграции:
его содержимое сохраняется, владельцы меняются вместе с остальными рабочими
каталогами и восстанавливаются при откате. Сам `tmp/` должен быть обычным
каталогом; проверки ссылок, hardlink и специальных файлов сохраняются.
Из прежнего Web firewall принимается только однозначное UFW-правило с
комментарием `Bot4VPS Web UI`; firewalld-порты без доказуемого владельца
сохраняются. Локальные Android build/signing каталоги сохраняются отдельно
в защищённом `development-artifacts`, если обновление заменяет дерево UI.

Проверки охватывают Telegram, Web, CLI и Mobile API; Android проверяется
своими unit/контрактными тестами. Проверка на физическом телефоне требует устройства.
CLI-bootstrap из тестовой/dev-копии вне `/opt/bot4vps` не заменяет системный
launcher. Старые self-backup с пустым контейнером venv и JSON-ссылками
поддерживаются без изменения защищённого venv и совместимых ссылок.
SQLite self-backup сохраняет аудит и связанные наблюдения операций;
исключаются только периодические ряды метрик.
