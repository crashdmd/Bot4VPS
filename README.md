# Bot4VPS

Telegram-бот для управления VPS и домашними серверами через SSH: мониторинг доступности и SSL, запуск скриптов, установка и управление сервисами на серверах (сейчас — WireGuard). Тот же функционал доступен через веб-интерфейс (FastAPI + SPA на ванильном JS) — по умолчанию оба работают в одном процессе поверх общего ядра.

> **Примечание:** проект создавался для личного использования, но может пригодиться и другим. При разработке активно использовались возможности ИИ.

# Возможности

## 🖥 Управление серверами

* Группы серверов (`home`, `vps`, свои группы) + управление самими группами: создание, переименование, настройка проверки SSL на уровне группы, удаление (с проверкой, что группа пустая — сервер молча в другую группу не переносится)
* Пошаговый мастер добавления сервера
* SSH-аутентификация по паролю или приватному ключу, быстрая смена типа авторизации
* Отдельный sudo-пароль при авторизации по ключу; при смене типа авторизации нужные параметры сохраняются автоматически
* Автоматическая проверка SSH при добавлении/редактировании, с возможностью сохранить сервер даже при неудачной проверке
* Карточка сервера: uptime, load average, RAM, диск — собираются одним SSH-запросом; понятные (не технические) причины ошибок SSH
* Перезагрузка, редактирование, удаление сервера
* Веб: тот же список серверов и карточка + встроенный SSH-терминал прямо в браузере (xterm.js поверх WebSocket, использует ту же SSH-обвязку, что и остальной бот)

## 🔑 Управление SSH-ключами

* Создание нового ключа (ed25519), вставка существующего приватного
* Просмотр содержимого, переименование, удаление с подтверждением
* Автоматическая проверка, что используемый ключ действительно существует

## 📡 Мониторинг

* Доступность серверов (online/offline) и SSL-сертификаты доменов
* Свой интервал проверки для каждого типа мониторинга, включение/отключение независимо друг от друга
* Уведомления в Telegram: сервер лёг/восстановился, сертификат обновился/скоро истекает
* Гибридная проверка доступности (ping, а если ICMP отключён — HTTP)
* Ручной запуск проверки из панели администратора или из веба
* В едином процессе изменение интервалов/вкл-выкл мониторинга через веб сразу переустанавливает jobs в работающем Telegram-боте — перезапуск не нужен

## 📜 Скрипты и фоновые задачи

* Запуск shell-скриптов через Telegram или через Web UI
* Параметры скрипта через комментарии в самом файле: `# BOT_PARAM <name> <type> [if=<param>:<value>] <label>` (типы `text`/`number`/`bool`/`select`) и `# BOT_OPTION` для значений select; условные поля показываются только когда выполняется `if=`
* Выполнение через `sudo`, живой вывод в процессе
* Task Manager: очередь задач на сервер, задача не блокирует ни бота, ни веб — можно продолжать пользоваться интерфейсом, пока она выполняется; общий механизм для скриптов и для операций сервисов (установка/удаление и т.п.)
* История задач, повтор/продолжение очереди
* Загрузка своих скриптов прямо файлом — через Telegram или через веб
* Автообновление данных о SSL после выполнения certbot-скриптов

## 🧩 Сервисы (Integrator)

Отдельный слой поверх core для управления конкретным ПО на сервере — сейчас это WireGuard, но фреймворк общий: новый сервис описывается контрактом (`Service`, `Parameter`, `service.json`) и подхватывается автоматически, без правки диспетчеров в Telegram или Web.

WireGuard-сервис умеет:

* установку и удаление сервера WireGuard, с проверкой пакетов/конфига/интерфейса, а не только кода возврата последней команды
* миграцию «классического» `wg0.conf` (руками накачанного или из другой панели) в формат бота — с резервной копией и откатом при сбое
* профили клиентов: добавление, удаление, переименование, включение/выключение, перевыпуск ключей — поштучно и массово (для профилей, импортированных при миграции)
* редактирование Endpoint/Port/Address/DNS с частичным изменением — трогается только то, что реально поменяли
* живую статистику (подключён/нет, последний handshake, RX/TX) без полной пересинхронизации конфигурации
* генерацию клиентского конфига и QR-кода; приватный ключ клиента собирается на самом сервере и в бота не попадает

## 🌐 Web UI

* Тот же функционал, что и в Telegram: серверы, SSH-сессии, очереди задач, скрипты с параметрами, мониторинг, WireGuard, файлы и ключи
* Дашборд с живым обновлением через SSE
* Встроенный SSH-терминал в браузере
* Журнал событий с полной информацией по записи (не только итоговая строка)
* Опциональная авторизация (выключена по умолчанию, рассчитана на локальный запуск): PBKDF2-хеш пароля, подписанная сессионная кука, смена пароля из интерфейса

## 🧾 Журнал событий

* Единая система событий для всего проекта: серверы, SSL, скрипты, задачи, сервисы, ключи
* Критичные события уходят уведомлением в Telegram
* Подробный просмотр отдельной записи (время, уровень, сервер, статус, технические детали вроде `task_id`/`reason`/`duration`)
* Очистка журнала вручную

# Конфигурация

`config.json` в корне создаётся автоматически с настройками по умолчанию при первом запуске — но токен и `allowed_users` всё равно нужно проставить руками:

```json
{
    "bot_token": "YOUR_BOT_TOKEN",
    "allowed_users": [
        123456789
    ],
    "monitor": {
        "online": { "enabled": true, "interval": 5 },
        "ssl": { "enabled": true, "interval": 1440 }
    },
    "web": {
        "auth_enabled": false,
        "username": "admin",
        "password_hash": "",
        "secret_key": ""
    }
}
```

Секция `web` нужна только если планируется использовать веб-интерфейс с включённой авторизацией — подробнее в `ui/web/README.md`.

Необходимые директории:

```bash
mkdir -p scripts keys backup logs
```

Данные о серверах и группах хранятся в одном файле `servers.json` (создаётся автоматически), при каждом изменении делается резервная копия в `backup/`.

# Запуск

Бот и веб теперь один процесс: `uvicorn` поднимает FastAPI, а в его lifespan запускается Telegram-бот (ручной lifecycle PTB — без своего `run_polling`, сигналами и event loop владеет uvicorn). Это основной способ запуска:

```bash
pip install fastapi uvicorn
PYTHONPATH=. uvicorn ui.web.app:app --host 0.0.0.0 --port 8080
```

Открыть: http://адрес_машины:8080/


Telegram запускается автоматически, если в `config.json` задан настоящий `bot_token` (не пустой и не заглушка `YOUR_...`) — иначе в логе будет `Telegram: token не задан — бот не запущен`, и поднимется только веб. Отдельно ставить или включать бота не нужно.

Task Manager, реестр сервисов и monitor jobs (`job_queue` бота) в этом режиме общие — задача, поставленная из Telegram, видна в вебе, и наоборот. Изменение интервалов мониторинга через веб сразу переустанавливает jobs в живом Telegram-приложении, без перезапуска процесса.

Если веб не нужен вообще (только Telegram, полностью автономный процесс):

```bash
PYTHONPATH=. python bot.py
```

Это отдельный процесс, независимый от веба (свой Task Manager, если веб не запущен параллельно) — используется, например, для минимальной установки без браузерного интерфейса.

# Автозапуск через systemd

Один юнит на единый процесс, `/etc/systemd/system/bot4vps.service` (файл уже есть в репозитории — `deploy/bot4vps.service`):
*Для текущего сценария установки Bot4VPS используется запуск от root, поскольку приложение выполняет административные SSH/сервисные операции на удалённых серверах.
```ini
[Unit]
Description=Bot4VPS (Web UI + Telegram bot)
After=network.target
Wants=network-online.target

[Service]
Type=simple
User=root
WorkingDirectory=/opt/bot4vps
Environment=PYTHONPATH=/opt/bot4vps
ExecStart=/opt/bot4vps/venv/bin/python -m uvicorn ui.web.app:app --host 0.0.0.0 --port 8080
Restart=always
RestartSec=5

[Install]
WantedBy=multi-user.target
```

Применить и проверить:
```bash
systemctl daemon-reload
systemctl enable --now bot4vps
systemctl status bot4vps
journalctl -u bot4vps -f
```

Если раньше стояли старые раздельные юниты (бот и веб по отдельности) — их нужно отключить, иначе Telegram запустится дважды (два `getUpdates` от одного токена конфликтуют):

```bash
systemctl disable --now bot4vps-web.service
systemctl disable --now bot4vps-bot.service   # или как назывался юнит бота
```

Подробности и заметки по нюансам reload — в `deploy/UNIFIED.md`.

# Архитектура

* **core** — вся бизнес-логика, ничего не знает ни про Telegram, ни про Web.
* **ui/telegram** и **ui/web** — два независимых UI-слоя поверх одного и того же core, на равных правах: что работает через Telegram, доступно и через веб (и наоборот), интерфейсы не дублируют логику, а вызывают одни и те же функции core. Физически по умолчанию это один процесс — `uvicorn ui.web.app:app` в своём lifespan сам поднимает Telegram-бота вручную (`bot.build_application()` / `start_telegram()` / `stop_telegram()`, без `run_polling()` — сигналами и event loop владеет uvicorn), поэтому Task Manager, реестр сервисов и monitor jobs общие для обоих интерфейсов. Полностью автономный Telegram без веба по-прежнему доступен через `python bot.py` (свой процесс, свой `run_polling()`).
* **Integrator** (`core/integrator.py`) — отдельное ядро для сервисов, которые ставятся и настраиваются на самих серверах (`services/*`). Ничего не знает о конкретных сервисах — только реестр, контракт `Service`/`Parameter`, запуск действий через Task Manager и JSON-кэш состояния. WireGuard — первый сервис на этом контракте; оба UI (Telegram и Web) ходят в него одинаково: `UI → Integrator → Service`, без своей копии бизнес-логики на стороне интерфейса.

  Состояние каждого сервиса на каждом сервере кэшируется в `data/services/<service_id>/<server_id>.json` — атомарная перезапись (temp-файл + fsync + `os.replace`), чтение через `read_cache()`/запись через `update_cache()`/`write_cache()`. Файл обновляется после операций, изменяющих состояние сервиса, и при явной синхронизации. Пример для WireGuard:

  ```json
  {
      "installed": true,
      "version": "wireguard-tools v1.0.20210914 - https://git.zx2c4.com/wireguard-tools/",
      "active": "active",
      "profiles": [],
      "endpoint": null,
      "needs_migration": true,
      "classic_peer_count": 3,
      "stats": { "online": 0, "total": 0, "rx_bytes": 0, "tx_bytes": 0 },
      "server_public_key": null,
      "address": null,
      "port": null,
      "dns": null,
      "service_id": "wireguard",
      "synced_at": "2026-08-10T10:27:39"
  }
  ```

  Это кэш для быстрого показа в UI (карточки, списки), а не источник истины — реальное состояние всегда на самом сервере по SSH. Если файла ещё нет или сервер не проверялся — читается как пустой объект, ничего не падает. Формат полей — на усмотрение конкретного сервиса (для WireGuard: `needs_migration`/`classic_peer_count` — признак ещё не мигрированного классического конфига, `stats` — сводка по профилям, остальное соответствует `wg0.conf`/`wg show`).

* **Task Manager** — общая очередь фоновых задач для скриптов и операций сервисов. Задача не блокирует работу ни Telegram, ни Web-интерфейса.
* **Event Service** — единая система событий и уведомлений. Модули мониторинга и сервисов не знают про Telegram напрямую: они создают событие, а `Event Service` записывает его в журнал, при необходимости кладёт в очередь уведомлений и отдаёт любому подписанному UI.

# Особенности

* При авторизации по паролю тот же пароль используется и для `sudo`; при авторизации по ключу sudo-пароль хранится и меняется отдельно.
* При смене типа авторизации бот сам подтягивает нужные параметры подключения — ничего вводить заново не нужно.
* Карточка сервера показывает понятную причину ошибки SSH вместо сырого исключения.
* Новый тип мониторинга или сервис добавляется без правки диспетчеров UI — оба интерфейса подхватывают его через общий контракт.
* Приватные ключи WireGuard-клиентов никогда не хранятся в самом боте — конфиг собирается на сервере, бот только скачивает готовый файл.
* Миграция классической конфигурации WireGuard делает резервную копию и откатывается сама при сбое на любом шаге.
* Веб-интерфейс работает без сборки — обычные статические HTML/CSS/JS-файлы, ничего компилировать не нужно.
* При старте/остановке Telegram внутри единого процесса реестр нотификаторов не копится — `register_notifier(replace=True)` и `clear_notifiers()` следят, чтобы уведомления не задваивались (актуально при `--reload` в dev).

# Безопасность

* Доступ к боту — только для пользователей из `allowed_users`.
* При каждом изменении `servers.json` создаётся резервная копия в `backup/`.
* SSH- и sudo-пароли нигде не отображаются в интерфейсе.
* Приватные SSH-ключи доступны для просмотра только через раздел управления ключами.
* Веб-авторизация опциональна и выключена по умолчанию (расчёт на локальный запуск); при включении — пароль хешируется PBKDF2-HMAC-SHA256, сессия — подписанная кука на 7 дней.
* Не рекомендуется выставлять Web UI непосредственно в Интернет без дополнительного reverse proxy/VPN и авторизации.

# Развитие проекта

Bot4VPS развивается по мере необходимости. Core, оба UI-слоя, сервисы, задачи и события разделены между собой — это позволяет добавлять новое (ещё один сервис, ещё один тип мониторинга, ещё один интерфейс) не трогая то, что уже работает.
